# Provenance and signing (14.2)

A checksum tells you two files are the same. It does not tell you where either
of them came from. If the download page and the checksum are served by the same
party, checking one against the other only proves that party was consistent —
which is exactly what an attacker who controls the page would be.

This is the layer that answers *where did these bytes come from*, and it has
three parts, each doing something the others cannot:

| | answers |
|---|---|
| **Reproducible build** (`REPRODUCIBLE_BUILDS.md`) | do these bytes correspond to this source? |
| **Provenance attestation** | which commit, workflow and runner produced them? |
| **Transparency log** | has that answer been given publicly, and to everyone alike? |

The third is the one people skip, and it is what makes the other two hard to
subvert. A signature you can check is a signature that can also be issued
quietly to one person; an entry in a public append-only log cannot be.

---

## Verifying a release

Every tagged release carries a SLSA build provenance attestation, signed
keyless through Sigstore and recorded in its public transparency log.

```
gh attestation verify z-linux-x64.tar.gz --repo FluffyHorizon1/z-messanger
```

That checks, without trusting the download page:

* the file's digest appears in a signed attestation;
* the attestation was produced by this repository's workflow, on a GitHub
  runner, from a named commit;
* the signing certificate was issued by Sigstore's CA to that workflow's OIDC
  identity, and the whole thing is logged in Rekor.

To go further and check the bytes correspond to the source, rebuild them —
`REPRODUCIBLE_BUILDS.md` has the procedure and `tool/verify_reproducible.py`
does the comparison.

### There are no signing keys to steal

Signing is **keyless**. The workflow mints a short-lived OIDC token, Sigstore
issues a certificate valid for minutes against that identity, and the
certificate and signature go in the log. There is no private key in a secret, on
a maintainer's laptop, or in a safe — so there is nothing to leak, nothing to
lose, and no key-rotation ceremony to get wrong. Compromising the release
identity means compromising the repository's workflow, which is visible in the
log as an attestation nobody expected.

Android is separate and does have a key: the Play upload key, and then Google's
own app-signing key. That is Play's model, not ours, and it is why
`apksigner verify --print-certs` is still the check for an APK — see
`SECURITY.md`.

## What is actually claimed — and what SLSA level this is

The roadmap asked for **SLSA Build L3**. What the configuration in
`.github/workflows/build.yml` delivers is **Build L2**, and the difference is
worth stating rather than rounding away.

* **L1** — provenance exists. ✅
* **L2** — provenance is generated by a hosted build service and signed by it,
  so it cannot be forged by whoever ran the build. ✅ This is what
  `actions/attest-build-provenance` on GitHub-hosted runners provides.
* **L3** — the build runs in an environment where the *build itself* cannot
  reach the signing material, so a compromised build step cannot forge its own
  provenance. ❌ Not yet.

Reaching L3 on GitHub means moving the build into a reusable workflow whose
provenance generation is isolated from the build steps (the `slsa-framework`
generators do this), so that a malicious dependency running inside the build
cannot mint an attestation about itself. That is a real change to how these
jobs are structured, not a flag, and it should be done deliberately.

**Until then this document, and any release notes, should say L2.** Claiming a
level the setup does not reach is the kind of thing that makes every other
claim here worth less.

## What provenance does not prove

* **Not that the source is good.** It proves these bytes came from that commit.
  Whether that commit is honest is what review and the audit (14.3) are for.
* **Not that the maintainer is honest.** A maintainer who tags a malicious
  commit gets perfectly valid provenance for it. What the log gives you is that
  they cannot do it *invisibly* — the attestation is public, permanent, and
  names the commit.
* **Not that your download is current.** Provenance says nothing about
  freshness; an attacker who serves you a genuine, correctly-attested *old*
  release with a known bug has attacked you successfully. See below.

## There is no in-app updater, and that matters here

The roadmap's 14.2 says *"the updater verifies signature and log inclusion
before applying"*. There is no updater. Android updates come through Play;
desktop builds are downloaded by hand from the releases page.

That is a legitimate design — an updater is a remote-code-execution channel
into every install, and not having one is a real reduction in attack surface
for a messenger. But it means the rollback protection an updater would give is
absent, and the honest statement is:

* **Android**: Play will not install an older `versionCode` over a newer one,
  so rollback is handled, by Google rather than by us.
* **Desktop**: nothing stops a user being served an older release. The
  mitigation is that the releases page lists versions and the attestation names
  the commit, so a user *can* tell — but only if they look.

If an updater is ever added, it must check provenance and log inclusion before
applying, and refuse a version older than the one installed. Until then this
gap belongs in the threat model's residual-risk column, not hidden behind the
word "signed".

## Reproducibility in CI

`.github/workflows/build.yml` builds the same commit twice, on two separate
runner VMs, in two differently-named checkout directories, and compares them
with `tool/verify_reproducible.py --ignore-signing-block`. This is the
cross-machine check `REPRODUCIBLE_BUILDS.md` could not perform in a container
with two cores.

The comparison ignores the APK signing block for a reason that is about keys,
not the build: a machine that has never signed an Android build generates its
own debug key on first use, so two fresh runners sign with different keys.
Everything outside the signature must match byte for byte — a single flipped
bit of app content fails the job, which was checked by flipping one.

| | |
|---|---|
| Reproducible build, same machine and path | measured (14.1) |
| Reproducible build, across runners | **measured, and it holds** (2026-09-09) — at a fixed checkout path; see `REPRODUCIBLE_BUILDS.md` |
| Reproducible build, across checkout paths | no — two libraries embed the build path (R16, accepted, bounded and documented) |
| SLSA provenance on release artefacts | **still not exercised** — the first tagged build reached the release job and died two steps before it (see below) |
| Sigstore keyless signing + Rekor log | via `actions/attest-build-provenance` |
| SLSA Build L3 | not reached; L2. See above |
| Updater verifying provenance | no updater exists |

This table has now been wrong in both directions on the same row, which is
worth leaving on the record. It first said the cross-machine job was "written,
not yet run", adding that a failure there would be *"a finding about the build
and not about the job"*. It ran on 2026-09-09 and failed, so the row said
FAILED. A redesigned three-way run then showed the machine was never the
variable at all: two runners at the same checkout path produce identical bytes,
and only the *path* changes anything. The row says what was measured, twice
corrected, and `REPRODUCIBLE_BUILDS.md` carries both the failure and the answer.

Why that matters here and not only there: provenance and reproducibility answer
different halves of one question. Provenance says *these bytes came from that
commit, on that workflow*. Reproducibility says *and you can rebuild them
yourself*. The second half now holds, on the stated condition that you check
out into a directory named `z` — so an attestation from this repository is
something an outsider can independently check, which is what it was always
supposed to mean.

The half still missing is that **nobody outside the project has done it**. That
is the phase-14 exit criterion and it cannot be self-certified.

## What the first tagged build found (2026-09-09)

The release job ran for the first time and **failed before publishing
anything**. No assets, no attestation, no release. Two things came out of it,
one good and one embarrassing.

The good one: the collection step's fix works. `SHA256SUMS.txt` listed the four
APKs, the AAB, the three desktop bundles and the screenshots — and **none of
the reproducibility artefacts**. The bug where a repro build's debug-key-signed
`app-release.apk` could overwrite the real one under the same name is
genuinely closed, confirmed on a real tag rather than by reading the diff.

The embarrassing one:

```
python3: can't open file '.../release/../tool/verify_reproducible.py'
```

The release job had always been pure downloads and uploads, so it had no
`actions/checkout`. Adding a step that runs a script out of `tool/` was enough
to break it, and nothing said so until a tag was pushed — which is the most
expensive moment to find out, because the version number is already spent.

It now checks out (sparsely, `tool/` only) **before** `download-artifact`,
since checkout cleans the workspace and the other order deletes what was just
downloaded. And because "remember that jobs need a checkout" is exactly the
kind of thing nobody remembers, `tool/check_workflow.py` now asserts it: any
job whose `run:` steps reference `tool/`, `docs/`, `protocol/`, `app/`,
`server/` or `scripts/` must have a checkout, and it must precede any artifact
download. It runs on every push, so the next occurrence fails in seconds
instead of on a tag. Both rules were verified by reintroducing the bug and
watching them fire.
