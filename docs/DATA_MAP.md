# Data map

Every piece of data Z creates: what it is, where it lives, who can read it, and
when it goes away.

A threat model argues about capabilities. This is the inventory underneath it —
the thing you check a claim against when the claim is "the operator learns
nothing". It is also what a data-protection question needs answering from, and
what an auditor should be able to read in one sitting.

Structured as **what** · **where** · **who can read it** · **how long**.

---

## On your device

The vault is a SQLite database sealed cell-by-cell with XChaCha20-Poly1305.
The key lives in the OS keystore (Keychain / Keystore / DPAPI / libsecret),
optionally behind an app passphrase. "Sealed" below means the individual cell
is encrypted, not merely that the file sits in an encrypted directory.

None of the above leaves the device by any automatic route. Android's Auto
Backup would otherwise copy the whole vault directory to the user's cloud
account, and on Android 12+ to a new phone by device transfer: the database
seals individual *cells*, so its structure — every message's direction,
timing and thread, every contact's routing id — is cleartext in the file, and
before Android 9 that backup had no end-to-end encryption. The manifest
refuses both (`allowBackup="false"`, `dataExtractionRules`), and
`tool/check_android_data_safety.py` refuses a manifest that stops doing so.
Identity moves between devices one way only: the archive above, which you
export deliberately.

**Deliberately not stored anywhere:** your contacts' phone numbers or email
addresses (Z never asks), a password for anything server-side (there is no
account), a handle's recovery code (shown once; the handle log holds only a
commitment to it), any analytics, and any crash reporter. There is no telemetry
endpoint in the app.

## In the relay's memory

The relay never writes to disk. `storage: 'ram-only'` in `/health` is a claim
you can check against `server/server.js` — the only `fs` use in it reads TLS
material.

Since 2026‑09‑11 the public relay is **two instances sharing one RAM‑only
key‑value store** (`render.ha.yaml`; Valkey with persistence off, reachable
only on the host's private network, no public address), so "the relay's
memory" is now two processes' RAM plus the store's. What lives where is in
the table; what changes for you is retention, not exposure: **a relay
restart or redeploy no longer loses the queue** — the queue is in the store
— and a *store* restart is what wipes it. Nothing is written to disk in
either place, and the store holds exactly the items below, in exactly the
same opaque form.

| What | Where | Who can read it | How long |
|---|---|---|---|
| Queued ciphertext envelopes, and per mailbox how many and how many bytes (the caps, §12.4) | RAM — or a RAM‑only Redis the instances share: per mailbox a list of entry keys, a hash of the entries, and their byte count. An attributed envelope's key names its sender, a sealed one's names nobody, and neither key holds anything the entry beside it did not (`SELF_HOSTING.md`, "Scaling out") | The operator sees opaque bytes and their padded size — not content; for a sealed envelope, not the sender either | Until delivered, until `QUEUE_TTL_HOURS` (72) after the relay accepted **that envelope**, or until the process (or the store) restarts — never evicted to make room |
| Which routing ids are connected, and the network address of every socket — the authenticated mailbox socket and the anonymous sender socket a device also holds (§12.1); and, for handles (phase 38), the socket a handle's owner reads its introduction mailbox on, authenticated as that mailbox and open only while it reads, and the anonymous socket each request to a handle is sent on, opened for that request and closed after | RAM — and, with several instances, *which instance* holds each mailbox's socket, in the store (`presence:{rid}`, 60 s, refreshed while connected) | Operator | While connected; the store's copy expires within a minute of the socket closing |
| That a sealed envelope arrived on an anonymous socket — never which identity sent it | RAM, transiently | Operator; nothing ties the socket to a routing id but its address (R21) | Duration of the send |
| Which routing id an envelope is addressed to, and when | RAM, transiently | Operator | Duration of delivery |
| Push tokens (FCM), if push is on and Z may show notifications — on Android push is on unless you turn it off, and since phase 41 a device registers only while notifications are allowed; until then it registered whether or not they were | RAM — or the store, so any instance can wake a device (`push:{rid}`) | Operator, and Google when a push is sent | 30 days after the app last registered it (`PUSH_TTL_DAYS`), until push is turned off or notifications are taken away (noticed at the next start or return to the foreground), or a store restart. A withdrawal made offline is said again on every connection until the relay answers; until phase 41 it was lost |
| That a routing id has authenticated here at least once — its mailbox is *owned* (phase 29, P0‑4), so it is not held to the first‑contact caps. RAM in single‑instance mode (at most `OWNED_CAP` of them); in the store a key `owned:{rid}` so it survives a relay restart | RAM — or the store (`owned:{rid}`). The same shape as `presence:`/`q:`/`push:` and no new identifier: the routing id is a hash the store already holds, nothing about who the person is | Operator | `OWNED_TTL_DAYS` (30) from the last authentication, or a store restart |
| That a routing id is an *introduction mailbox* (phase 37, `PROTOCOL.md` §21.6) — the mailbox a handle resolves to, flagged by its owner — and the proof‑of‑work difficulty the owner set: a routing id and a number. A flagged routing id holds no push token. The stamp a send to it carries is checked and dropped: never stored, logged or forwarded, and it names no sender. Beside each envelope it holds that came with a stamp — in practice, those for such a mailbox — the SHA‑256 of that envelope's payload, to recognise a copy: a hash of ciphertext it holds anyway, kept only as long as the envelope | RAM, kept with the owners above (at most `OWNED_CAP`) — or the store (`intro:{rid}`, beside `owned:{rid}`) | Operator | `OWNED_TTL_DAYS` (30) from the owner's last `intro` frame, or a store restart (in RAM, a relay restart) |
| Per‑address counters (phase 29, P0‑4/P1‑13): the bytes each client address sent to mailboxes nobody owns in the current minute, and how many sockets it holds open — an address and a number, never a routing id or a destination. The address is `CLIENT_IP_HEADER`'s value when configured, else the socket's | RAM, per instance | Operator | The minute it counts (pruned at the next sweep, so about two minutes at most); the socket count while the sockets are open |
| Relay‑wide counters, with no routing id in any: logins (`z:reg`), mailboxes created in the store's current minute with `NEW_MAILBOX_SHARED=on` (`z:nm`, two integers), and the total unowned bytes held (`z:ub`, one integer the sweep reconciles) | The store | Operator | until the store restarts (`z:ub` carries a short TTL so it clears if sweeps stop) |
| Aggregate counters (`/metrics`) | RAM, per instance — each instance counts its own work. Counts only: envelopes, refusals of each kind, acknowledgements that matched and that did not (`z_ack_miss_total`), delivery latency buckets, and a `z_relay_info` line labelled with the instance id/coordinator/push — no routing id appears in any of them | Only a scraper with the `METRICS_TOKEN` bearer: `/metrics` answers 404 without it (P1‑14), so the aggregate counters are not a presence oracle for the internet | Until that instance restarts |

**Not held by the relay at any point:** message content, sender identity
(sealed sender), display names, group membership, contact lists, any key
material, or any log of who talked to whom. Restarting everything loses
everything, which is the intended behaviour rather than a limitation — and
with a shared store that now takes restarting the store, not just the
relay.

| **Cloudflare** (in front of the public relay and the public log) | TLS ends at Cloudflare, so it sees what the relay and the log see at the network level, beside each client's IP address: the routing id a device authenticates as, the `to` of every sealed envelope and its padded size, push tokens as they are registered, and every request the log answers. Not content or senders — envelopes are end-to-end encrypted and sealed inside the TLS it terminates (`THREAT_MODEL.md` R44) | The public deployment's DNS, TLS and proxy | Yes — a self-hosted relay and log need nothing in front of them; whether the public deployment keeps it is undecided |

The app makes no other network calls. It contacts the relay you configure,
the transparency log — `kt.zmessengers.com` unless you change it (HTTPS: the
log's head, the buckets your contacts fall in among decoys, the entries new in
them and this account's own entries, up to four times a day — at a random
moment in each six‑hour window, or, on a phone almost always, a few seconds
after the app is opened; none when no
log is set) — the handle log, if one is set (none is in this build), only

## What leaves your device, and in what shape

| Leaving | Shape on the wire | Visible to the relay |
|---|---|---|
| A message | Sealed envelope, padded to one of six buckets | Its recipient, its arrival time, its bucket |
| An attachment | Chunks sealed under a per-file key, padded | Same, per chunk |
| Your device list | An inner message inside the ratchet, 4 096 bucket | Indistinguishable from a chat message of ~190–1 900 characters |
| Your post-quantum device-list signature | Its own inner message, 16 384 bucket, on a delayed schedule (`adr/0004`) | A ~16 KB envelope at an unrelated time — see R2 in `THREAT_MODEL.md` |
| Your post-quantum identity key | An inner message, 16 384 bucket, early in a new conversation | A ~16 KB envelope, as a text of 2 000+ characters would be (`adr/0004`, addendum) |
| A delivery or read receipt | Inner message: the 1 024 bucket naming one to three messages, 4 096 naming four to sixty‑four (measured, `adr/0028`) | Same as a short message, or one of a hundred characters or more; and when — since phase 41 never sooner than 5 s after the message it answers, at a random moment up to a minute (`adr/0028`) |
| A contact request to a handle (phase 38) | A sealed envelope to the handle's introduction mailbox, padded, with a proof‑of‑work stamp beside it, on an anonymous connection opened for it and closed after | Its recipient — the introduction mailbox, which anyone who looks the handle up can compute — its arrival time, its bucket and the address it came from; the stamp is checked and dropped |

## Erasure

| To remove | Do this | What survives |
|---|---|---|
| One message, on this device | Delete for me | Nothing in the vault: the row, the attachment's row, its blob, its chunks, the reactions and the delivery receipts all go together, and a backup taken afterwards does not carry them. What the storage hardware retains is R28 |
| One message, everywhere | Delete for everyone | Nothing on honest clients; a malicious client can keep anything it received. The same from a linked device: a delete (or an edit) sent from one is the sender's on every device of the other side. Until 30.1 (deletes) and 30.3 (edits) the other side's devices dropped it, so the text stayed there (the 2026‑10‑03 review's P1‑12) |
| A contact and its history | Delete contact | Nothing locally but what the groups hold, and one transparency decoy (below). What a group chat holds of them stays in that chat, as anyone's does — their messages (sealed, with their name and routing id), their reactions and their confirmations of yours (each naming their routing id in the clear), and the chat's own lines that name them (sealed, by name). And while a group you are in still names them — as a member, or as an admin who has left — its sealed record keeps their routing id, public key and name, which its lists go on naming them by: deleting a contact takes nobody out of a group, and a list of yours that dropped an admin would be refused by every member. A change someone else makes to such a group meanwhile adds them back as a contact, as it does any member. That ends when they are out of the group, when you remove them, or when you leave it or are removed: a group you are out of keeps nobody you deleted, as its owner or its last list's issuer included, so a contact named only by groups you have left gets the plain dialog and is wiped as it says. The delete dialog says so and names the groups; `contact_erasure_test.dart` 6–13 search the whole vault, sealed values opened, for exactly that. Their copy is theirs. Until 2026‑09‑17 this row was false: the tables went and every `kv` family keyed by their routing id stayed — their account key, their devices' public keys with the list's version and signature, the post‑quantum material, the ratchet with their linked devices, the alerts and what the log said — unsealed wherever the family is declared plain, for the life of the install, and a contact added back met their own stale list version. The families are one declared list now (`ChatService.contactKvFamilies`), removed together with the rows, and `contact_erasure_test.dart` searches the whole vault for the routing id afterwards. It was still not quite true until 2026‑09‑20: the deletion took no lock, so a send already in flight — sealed and one step from its transaction — could commit INTO the sweep and leave the envelope, the message row or a fresh conversation behind, which is what failed the 3.9.0 release build. The deletion now runs under the same per‑contact lock a send holds, and a send that was queued behind it writes nothing. The receive side does not yet look again: a message of theirs that was already being received when the deletion ran can still write its conversation, its message and its dedupe entry after the sweep — their content sealed, shown nowhere. And since phase 35 the transparency log's decoys keep, marked as nothing else among them, a value inside the log bucket the contact's label fell in — one of 32 to 64 accounts — so that the deletion changes nothing the log is asked (`adr/0023`) |
| Everything on this device | Uninstall, or reset identity in Settings | Backups you made yourself; whatever your contacts hold; and a handle you did not give up first, which stays in the handle log taking requests nobody reads until its recovery code moves it to a new install |
| Your presence on the relay | Stop connecting | Nothing — the relay holds no account, and the record that you were connected expires within a minute |
| Your handle | Settings › Your handle › Give up handle | Every record the handle log accepted for it, for good — a log that forgets is not a log — so the name stays, its last record taking no requests, and nobody else can claim it; its recovery code can bring it back. This device forgets its keys; requests that came through it and still wait stay until you answer them. The relay's flag on its introduction mailbox lapses `OWNED_TTL_DAYS` (30) after the app last renewed it |

There is no "delete my account" request to send, because there is no account to
delete: no server-side record exists to be erased — unless you claimed a
handle, whose records the handle log keeps for good (above). That is a stronger position
than a deletion policy, and it is worth stating in those terms when someone
asks the GDPR question — the lawful-basis conversation is short when the
processor holds ciphertext addressed to a hash, in memory, and forgets it on
delivery, on expiry (`QUEUE_TTL_HOURS`, 72), or when that memory goes.
