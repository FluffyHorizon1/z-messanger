# ADR 0016 — A camera and gallery picker for attachments

**Status:** **Accepted** (2026‑09‑19) — built (continuous‑b, capture half).
Android only; iOS and desktop are unchanged.
**Decides:** how a photo or a gallery video is attached without a trip through
the generic file browser, and how that keeps the vault invariant that every
other attachment keeps.

## Context

Attaching media has been one path: the generic file browser (`file_picker`),
on every platform. To send a photo you take it in the camera app, then hunt for
it in the file browser. continuous‑b (b) asks for the direct path a messenger is
expected to have — a **Camera** and a **Photo/video** entry beside **File**.

The reason this is an ADR and not a one‑line dependency is the invariant it
sits next to. Z's vault invariant is that decrypted content is never written to
disk in plaintext; attachments are read into memory, sealed, and sent. A media
**picker** works against that grain: `image_picker` (and `file_picker` on
Android) does not hand over the file the user chose — it **copies** it into an
app cache directory outside the vault and returns that copy. A copy left there
is plaintext that outlives the sweeper, the disappearing‑message timer and
"reset identity" alike. So the question is not "can we pick a photo" but "does
the pick leave a plaintext copy behind".

There is a second constraint that shapes the scope: iOS‑track files are not
touched in this line of work, and a camera/gallery picker on iOS and macOS needs
per‑platform configuration (Info.plist usage strings, macOS entitlements) that
the file picker does not. Adding those is an iOS‑track change.

## Decision

Add **`image_picker`** and offer **Camera / Photo‑or‑video / File on Android
only**. The attach button on Android opens a three‑item sheet
(`chat_screen.dart` `_attach` → `_attachFromPicker` / `_attachFile`); **every
other platform goes straight to the file browser exactly as before** — which is
where `image_picker` would fall back to anyway, and which needs none of the
per‑platform camera config.

**The picker's plaintext copy is deleted the moment its bytes are read.**
`readAndDeletePicked` (`core/picked_file.dart`) reads the copy into memory and
then unlinks it, best effort; `_attachFile` does the same for the file path via
`FilePicker.clearTemporaryFiles()`. Nothing the picker copied outlives the read.

**Picked media rides the same pipeline as any attachment.** `_attachFromPicker`
and `_attachFile` both end at `_sendPicked`, which calls the existing
`sendFile` / `sendGroupFile`. The `maxAttachmentBytes` cap, the sealing, and the
error handling are unchanged and live in one place — capture is a new *source*
of bytes, not a new send path.

**No new permission and no new platform config.** Camera capture reuses the
`CAMERA` permission the manifest already declares (for the QR scanner); the
gallery path (`pickMedia`) uses Android's system photo picker and needs none.
No Android, iOS or macOS project file is modified by this change.

## Rejected

- **Enable capture on iOS/macOS too.** The natural symmetric choice, and the
  reason it is not taken is the iOS‑track boundary plus the Info.plist /
  entitlement config a camera picker requires there. Left for an iOS‑track
  change; desktop keeps the file browser, which is the right affordance there
  anyway.
- **Let the picker's cache copy be swept later instead of deleted now.** Relies
  on the cache sweeper running before the device is compromised or seized — a
  window the vault invariant exists to close. Delete at read time, not
  eventually.
- **A custom in‑app camera.** Owning a camera stack (preview, orientation, codec)
  for this is far more surface than a maintained picker that returns a file, for
  no security gain — the bytes still have to be read and sealed either way.
- **Leave it as file‑browser‑only.** The status quo, and defensible, but "attach
  a photo" going through a file hunt is the gap continuous‑b names.

## Consequences

- **Supply chain.** `image_picker` pulls **13 packages** transitively:
  `image_picker` and its federated platform packages
  (`image_picker_android`, `_ios`, `_linux`, `_macos`, `_windows`,
  `_for_web`, `image_picker_platform_interface`), the `file_selector_*` set the
  desktop/web fallbacks use (`_linux`, `_macos`, `_windows`,
  `file_selector_platform_interface`), and `mime`. The `_ios`/`_macos` packages
  are in the closure because the plugin is federated, but no iOS/macOS capture is
  wired and no iOS/macOS project file changed — the UI gates on
  `Platform.isAndroid`. All pinned in `pubspec.lock`; no credentials, no config,
  nothing at rest. No `.so`: unlike media_kit (0013) these are Dart + platform
  SDK code, so the picker adds no bundled native library.
- **Android build/registration.** Android plugin registration is generated by
  the Flutter Gradle plugin at build time, not a committed file, so no
  `android/` file changed. The **desktop** plugin registrants
  (`linux`/`windows`/`macos`) regenerated to list the picker's desktop fallback
  plugins — the same mechanical regeneration `flutter pub get` always does.
- **Android reproducibility.** No new native library is bundled, so the APK's
  `.so` set is unchanged; the `reproducible` / `reproducible-compare` jobs'
  fingerprint set is expected to be unaffected. (To confirm on CI, not asserted
  here — image_picker_android adds Kotlin/Java, which lands in the dex, not a
  new `.so`.)
- **Metadata / sealed sender / ratchet / wire / relay:** untouched. A picked
  photo is sealed and sent as any file is; nothing new crosses the wire, nothing
  new is logged or stored server‑side, and the relay learns no more than it did
  for a file attachment.
- **iOS:** unchanged. The capture UI does not appear there; the iOS track picks
  up camera/gallery when it chooses to add the platform config.

## What was verified, and what is device‑gated

- **Verified here:** dependency resolution and the regenerated desktop
  registrants; `flutter analyze` clean on `chat_screen.dart`; the l10n and a11y
  guards; `readAndDeletePicked` tested (bytes returned, plaintext copy gone, and
  a delete that cannot happen still returns the bytes); the full app suite green,
  so the `test` CI job is unaffected and nothing regressed. The
  CAMERA‑permission‑already‑present and no‑iOS‑files‑touched claims were checked
  against the tree.
- **Device‑gated (the pusher/QA confirms on hardware):** the actual camera and
  system‑photo‑picker flow on an Android device, and that a large capture trips
  the `maxAttachmentBytes` cap with the existing error path — the sandbox has no
  camera or Android runtime. This is a UI‑on‑hardware check, not a claim about
  secrecy.

## Not in this half: playback

continuous‑b's **playback** half — inline video, rather than Save‑to‑device — is
a separate change and a separate ADR. `video_player` has no in‑memory source, so
playing a received video inline without spilling plaintext to disk needs the
same loopback‑HTTP‑server route the voice notes use (0013), which is a design
point worth its own record. This half is capture only.
